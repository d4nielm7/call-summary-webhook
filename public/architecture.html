Overview

The whole system on one page

A receptionist sends in a call summary. The server checks it and stores it once. Staff watch it arrive on a dashboard.

1 · System in detail

The same system, down to the files

Everything runs in one process with one database file. The blue path is the brief: receive, validate, de-duplicate, store. The grey paths exist so the work can be seen and demonstrated.

2 · Request path

Every call passes five gates, and the last step is a single statement

Each gate can end the request with its own status code. The order puts the cheapest and most security-relevant checks first, so an unsigned request costs almost nothing.

3 · Data

The database enforces the duplicate rule, not the code around it

Two UNIQUE constraints decide what counts as a repeat, and one statement does the check and the write together. Two identical calls arriving at the same instant, even in two processes, can only produce one row.

calls one row per real call

idTEXTPRIMARY KEY
call_idTEXT, nullableUNIQUE the sender's id
fingerprintTEXTUNIQUE phone + slot
caller_nameTEXTwhitespace collapsed
phoneTEXTE.164
reasonTEXTup to 1,000 chars
requested_timeTEXTUTC, ISO 8601
received_atTEXTUTC

events one row per delivery attempt

idINTEGERPRIMARY KEY
atTEXTUTC, indexed
outcomeTEXTcreated, duplicate, invalid, unauthorized
call_refTEXT, nullablepoints at calls.id
matched_onTEXT, nullablecall_id or slot

It holds no caller data, which is what lets the dashboard count refused and repeated deliveries without storing personal data twice. Rows older than the latest 20,000 are pruned on insert, so a flood of bad requests cannot grow the file without limit.

fingerprint = sha256( phone_e164 + "|" + requested_time_utc )

INSERT INTO calls (...) VALUES (...)
ON CONFLICT DO NOTHING        -- call_id or fingerprint already present? then nothing is written
-- changes = 1  → 201 created      changes = 0  → look up the existing row → 200 duplicate

The caller's name and the reason are left out of the fingerprint on purpose. Speech-to-text spells the same person differently ("Jon", "John") and a language model never words a summary the same way twice, so including them would let real repeats through.

5 · Security

Each boundary has one control and one test that proves it

The data is personal (names and phone numbers), so every place it crosses a boundary has a check. The last line of each card is the name of the automated test that would fail if the control were removed.

Who may send a call

The sender signs the raw body with a shared secret. The server recomputes the signature and compares in constant time, before it parses anything.

test 401s a missing, wrong or mismatched signature and stores nothing

What may be stored

Every field is cleaned and checked. Errors name the field but never repeat the value, so personal data is not echoed back or logged.

test does not echo caller data back in the error response

Two calls at once

The database's unique keys decide, in the same statement that writes. There is no gap between checking and saving for a second call to slip through.

test only one of many simultaneous identical deliveries is stored

Who may read the dashboard

The page and its files hold no data. The data endpoint needs a bearer token, hashed and compared in constant time. With no token configured it answers 404.

test 401s a missing or wrong token

What the browser may run

Caller text is only ever put on the page as plain text, never as markup, and a strict Content-Security-Policy blocks inline scripts and framing.

tests never builds markup from strings · serves the page with a locked-down content security policy

Which files are served

Only a short list of named paths is served. A request path is never turned into a file read, so nothing else in the project is reachable.

test serves nothing outside the allowlist, whatever the path

The demo controls

The route that makes up fake calls exists only when demo mode is on. On a real server it answers 404, even with a valid token.

test does not exist unless demo mode is on

What the logs hold

One line per request with the outcome, an id and the names of failed fields. Never a name, a number or a reason.

test never logs caller data
6 · Decisions

The choices that were made, and what each one costs

DecisionWhyCost, and what changes at scale
SQLite in one fileReal storage that can enforce uniqueness, with nothing to install. A reviewer runs it in one command.Needs a persistent disk. On serverless hosting, swap CallStore for Postgres and keep the same two UNIQUE keys; nothing else changes.
A duplicate answers 200Senders retry anything that is not a success. An error would make them retry again.The status alone cannot tell the sender it was a repeat. The body says so, with the original id.
Duplicate key is call id, or phone plus slotNames and summaries change between calls; a phone number and a requested time do not.Two people calling from one number for the same slot become one record. The reply names the original, so nothing fails silently.
Requested time must carry a timezone"3pm" has no meaning without one, and guessing in the server's timezone would store wrong appointments.Sloppy senders get a 422 they cannot retry past. That is intended.
Static page, one JSON endpoint, no frameworkNothing to build, and a strict security policy is easy to hold.Charts are hand-drawn. The server side is fully tested; the page was checked by hand in a real browser.
Numbers added up in JavaScriptSimple and correct at appointment-inbox volume (thousands of rows).At much larger volume, move the GROUP BY into SQL.
A separate events tableMakes blocked and refused deliveries countable without storing personal data twice.One extra write per delivery. A failure to log is caught and never fails the call.
Every name and number in the demo is fictional sample data.
